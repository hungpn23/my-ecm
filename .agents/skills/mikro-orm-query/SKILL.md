# MikroORM queries in my-ecm

Inspect the owning service, contract, callers, and existing query patterns before changing data access. Apply `design-principles`; use `mikro-orm-schema` for entity metadata and database schema decisions.

- **Ownership:** Apply the required tenant or user scope to each owned-resource read and mutation, using the authenticated context. `ProductService` filters shop-owned products by `ShopContext.shopId`; `AddressService` uses the authenticated user. A policy alone does not scope a query.
- **Dynamic conditions:** Combine dynamic filters with an array of conditions and `$and`. When there are no conditions, handle the empty case explicitly, as `CategoryService.find` returns `{}`. Within a condition, use other operators such as `$or` when needed for the intended semantics.
- **Search:** Preserve input as-is in the agreed product and category `$ilike` searches. SQL `%` and `_` act as wildcards; do not add an escape helper to these searches. Consider different search semantics only when required by the task.
- **Transactions and contexts:** For every service handler that accesses the database, including read handlers and RPC service handlers, use an explicit `this.em.transactional(...)` transaction. Perform its database operations with the callback's `em`; do not substitute a standalone `fork()` and `flush()` for the explicit transaction. Keep external effects that must follow commit outside the transaction.
- **Identity map and refresh:** Before adding `refresh: true`, trace the entity manager and identity map used by the operation and establish whether the entity could already be loaded there with stale state. Separate requests do not by themselves share an identity map. A pessimistic lock and refresh serve different purposes; do not add refresh solely because concurrent requests exist. Consider the effect on unflushed changes.
- **Concurrency:** Identify the shared invariant and competing operations before choosing a lock. `AddressService` locks the user inside the transaction before changing addresses. Preserve the lock and transaction scope when modifying that flow; assess and validate concurrency for the specific change.
- **External effects:** Emit events or perform other external side effects after the relevant transaction commits when they must not occur on rollback. After-commit emission alone does not guarantee delivery or retry; account for failure after commit according to the requested reliability.
- **Ordering and pagination:** Add a stable tie-breaker when a deterministic order matters, as in `ProductCatalogService`. Offset pagination can still shift when data changes. Preserve the existing offset and metadata formulas; do not introduce a pagination helper solely because they repeat.
- **Loaded relations:** Match `populate` to the relations required by entity methods and use `Loaded<...>` to express those requirements, as in `ProductEntity.toDetailResponse`. Do not assume relations are always loaded.
- **Entity and service:** Keep behavior derived from entity state in the entity, such as a computed getter, and put entity-to-response mapping in `toResponse` or a suitably named `to...Response` method. Services coordinate queries, transactions, and I/O, then call the entity method. Follow existing entity serializers using `wrap(this).serialize(...)`, excluding relations or fields that are not part of the response and adding computed getters explicitly where needed. Prefer direct `EntityManager` use and introduce a repository or shared query abstraction only for a concrete need that improves clarity or maintainability.
- **Entity responses:** For an entity's `toResponse`, use its response schema composed with `EntityResponse`; keep entity fields such as `id`, `createdAt`, and `updatedAt`. Use a `*FromRpc` schema to parse values received from RPC, not as the producer's response schema. Give partial projections a distinct schema and method name.
- **Query and response projections:** Express the loaded or excluded properties required by an entity method with `Loaded<Entity, Populate, Fields, Excludes>` and align its `this` type with the query options and serialization. For example, excluding `reservations` can be reflected in the fourth type parameter as well as in `wrap(this).serialize({ exclude: [...] })`. Query `exclude` omits columns from the loaded entity; serialization `exclude` removes fields from the response. Keep every field needed by a getter or method loaded even if it must be excluded from the response. Do not assume a passing type check proves those runtime dependencies are loaded.

Verify query scope, callers, and response contracts. Distinguish source inspection from actual database, concurrency, or end-to-end validation.
